# 02. Архитектура бэкенда (Go)

## Принципы

- **Тонкие Wails-сервисы, толстые пакеты домена.** Сервис не содержит бизнес-логики:
  валидирует вход, вызывает домен, возвращает DTO.
- **Контекст везде.** Все длительные операции принимают `context.Context` и завершаются по отмене.
- **Ошибки оборачиваются** через `fmt.Errorf("...: %w", err)`.
- **Никаких глобальных изменяемых синглтонов**; зависимости передаются явно (конструкторы).

## Структура каталогов

```
main.go                      # точка входа: создание app, окна, регистрация сервисов/событий
internal/
  app/        # конфигурация Wails-приложения, окно, жизненный цикл
  paths/      # каталоги ОС (config/data/cache), пути к зависимостям
  config/     # модель настроек, загрузка/сохранение JSON, дефолты
  history/    # история задач (JSON)
  deps/       # менеджер зависимостей (единый интерфейс + реализации)
    ytdlp.go
    ffmpeg.go
    deno.go
    manager.go
  ytdlp/      # построение команд, запуск процесса, парсинг прогресса
  proxy/      # модель пула, ротация, health-check
  download/   # очередь задач, оркестрация, ретраи со сменой прокси
  events/     # имена событий и типы их payload'ов
  services/   # Wails-сервисы (адаптеры над доменами)
    download_service.go
    deps_service.go
    settings_service.go
    proxy_service.go
```

### Правила зависимостей между пакетами

- `services` → домены (`download`, `deps`, `config`, `proxy`).
- Домены не зависят от `services` и от типов Wails (кроме `events`).
- `paths`, `config`, `history` — низкоуровневые, не тянут домены.
- `ytdlp` зависит от `deps` (для пути к бинарнику) и `paths`.

## Wails-сервисы

Каждый сервис — структура с методами, экспортируемыми во фронтенд (генерируются TS-биндинги).

| Сервис | Отвечает за |
|--------|-------------|
| `SettingsService` | чтение/запись настроек, выбор папки загрузки |
| `DepsService` | статус, установка, обновление зависимостей |
| `DownloadService` | создание/отмена задач, очередь, запрос форматов |
| `ProxyService` | CRUD пула прокси, health-check, выбор стратегии |
| `HistoryService` | чтение/очистка истории |

> Имена методов и DTO фиксируем в `06-conventions.md` как единый стиль (PascalCase методы,
> DTO-структуры с TS-совместимым JSON).

## События (Go → Frontend)

Прогресс и статусы стримятся событиями. Имена — в пакете `events`, payload'ы типизированы и
заранее зарегистрированы (`application.RegisterEvent[T]`), чтобы биндинги были строго типизированы.

| Событие | Payload | Когда |
|---------|---------|-------|
| `dep:progress` | `{ name, phase, received, total }` | скачивание/установка зависимости |
| `dep:state` | `{ name, version, status }` | смена статуса зависимости |
| `task:progress` | `{ taskId, downloaded, total, speed, eta, ... }` | ход загрузки |
| `task:state` | `{ taskId, state, error? }` | смена состояния задачи |
| `proxy:health` | `{ proxyId, ok, latencyMs }` | результат health-check |

### Троттлинг

Прогресс `yt-dlp` парсится построчно и **агрегируется**: события шлются не чаще N раз/сек
(например, ~4–10 Гц) и только при изменении значимых полей. Это защищает webview от шторма
перерисовок. Реализация — в `ytdlp` (агрегатор) + дебаунс перед `Emit`.

## Парсинг прогресса `yt-dlp`

Используем машинно-читаемый вывод, а не «человеческий» stdout:

- `--newline` + `--progress-template` (JSON-шаблон) → стабильный поток строк;
- `--print`/`-J` для метаданных и списка форматов;
- `--no-color`.

Конкретно прогресс помечается префиксом `loadika-progress:` и содержит JSON-объект `%(progress)j`
(см. `internal/ytdlp/args.go`); парсер снимает префикс и разбирает JSON.

Подробные аргументы и шаблон фиксируются в отдельном модуле `ytdlp/args.go` (чистые функции,
легко тестируемые).

## Отмена и завершение процессов

- Каждый запуск `yt-dlp` привязан к `context.Context`.
- Отмена задачи — `context.CancelFunc` → сигнал процессу (graceful, затем kill по таймауту).
- При закрытии приложения все процессы корректно завершаются (lifecycle-hook Wails).

## Ошибки и пользовательские сообщения

- Домен возвращает типизированные ошибки (например, `ErrNetwork`, `ErrProxyExhausted`,
  `ErrDependencyMissing`).
- Сервис конвертирует их в DTO `{ code, message }` с человекочитаемым текстом для UI.
